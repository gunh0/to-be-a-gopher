# 20. Mutual TLS

> **Abstract.** Mutual TLS gives each service a cryptographic identity, but `crypto/tls` only authenticates what it is told to: `RequestClientCert` and `RequireAnyClientCert` accept any certificate, `VerifyClientCertIfGiven` accepts no certificate, and `r.TLS.PeerCertificates` holds whatever the client *presented*. The secure combination is `RequireAndVerifyClientCert` with a dedicated client CA, followed by an authorization decision on a **verified** identity — a SPIFFE ID in the URI SAN read from `VerifiedChains` — never on the Subject CN. Handshake success is authentication; whether that identity may call this endpoint is a separate check that returns 403.

## 1. Threat model

Internal services call each other over mTLS instead of bearer tokens. The attacker has a foothold inside the network (a compromised pod, a CI runner, a developer laptop) and can open connections to any service. They can mint self-signed certificates with any subject, may hold a legitimate certificate for a low-privilege service, and want to call a high-privilege endpoint (billing, admin, secrets).

## 2. What `crypto/tls` does for each `ClientAuth` value

| `ClientAuth` | Certificate required | Chain verified against `ClientCAs` | `VerifiedChains` populated |
|---|---|---|---|
| `NoClientCert` (default) | no | — | no |
| `RequestClientCert` | no | **no** | no |
| `RequireAnyClientCert` | yes | **no** | no |
| `VerifyClientCertIfGiven` | **no** | if one is sent | only if one is sent |
| `RequireAndVerifyClientCert` | yes | yes | yes |

Verification checks the chain, validity and the `clientAuth` extended key usage (a `serverAuth`-only certificate is rejected, `TestRequireAndVerify`). It does **not** check revocation, and it has no notion of which identities may call which endpoint. `PeerCertificates` is filled for every mode that receives a certificate, verified or not; `VerifiedChains` only after successful verification.

In TLS 1.3 the client finishes its side of the handshake before the server has verified the client certificate, so a rejection surfaces at the client as an error on the first read or response, not from `Handshake`.

## 3. Insecure pattern

[`ServerConfigUnsafe`](mtls.go) + [`AuthorizeByCNUnsafe`](mtls.go):

```go
ClientAuth: tls.RequestClientCert                 // asks, does not verify
...
r.TLS.PeerCertificates[0].Subject.CommonName == "billing"
```

`TestUnverifiedCNIsSpoofable`: a self-signed certificate with `CN=billing`, generated by the attacker, is authorized. Each of the three mistakes is enough on its own:

- **Unverified certificates**: `RequestClientCert`/`RequireAnyClientCert` are for applications that verify in `VerifyPeerCertificate` themselves.
- **`PeerCertificates` instead of `VerifiedChains`**: reads what was presented, not what was verified.
- **CN as identity**: a free-text field. A CA issuing "service certificates" usually constrains SANs, not CN, and two services can share a CN.

`VerifyClientCertIfGiven` is often chosen so health checks or browsers can connect without a certificate. Then a client without a certificate completes the handshake, and the handler is the only defence (`TestVerifyClientCertIfGivenLetsAnonymousThrough`): middleware that assumes "TLS handled it" lets anonymous requests through.

## 4. Secure pattern

[`ServerConfig`](mtls.go) and [`Require`](mtls.go):

```go
&tls.Config{
	ClientAuth: tls.RequireAndVerifyClientCert,
	ClientCAs:  clientCAPool,        // dedicated client-issuing CA
	MinVersion: tls.VersionTLS13,
}
mux.Handle("/invoices", mtls.Require("example.test", []string{"spiffe://example.test/ns/prod/sa/billing"}, invoices))
```

1. **`RequireAndVerifyClientCert`** with a **dedicated client CA** in `ClientCAs`, not the system pool and not the server-certificate CA. Whoever can obtain a certificate from `ClientCAs` can authenticate.
2. **Identity from `VerifiedChains[0][0]`**, which is empty unless verification succeeded, so the check fails closed under any weaker `ClientAuth` mode.
3. **Identity is a URI SAN** in SPIFFE form, `spiffe://<trust-domain>/<path>`. [`SPIFFEID`](mtls.go) requires exactly one URI SAN (as the X.509-SVID spec does), the `spiffe` scheme, the expected trust domain, a path, and no userinfo, query or fragment. DNS SANs work the same way when service identities are DNS names.
4. **Authorization per endpoint**: no verified identity → 401; verified but not allowed → 403. The table in `TestRequireAndVerify` covers no certificate, foreign CA, self-signed, wrong EKU (all rejected in the handshake), wrong SPIFFE ID with a matching CN (403), foreign trust domain (401), and the allowed identity (200).
5. **Short-lived certificates instead of revocation.** Go does not consult CRLs or OCSP. SPIFFE implementations issue SVIDs valid for hours and rotate them automatically; a stolen certificate expires quickly. If revocation is required, check a CRL in `VerifyConnection`.

## 5. Where the guarantee ends

- **Terminating proxies.** If a load balancer or sidecar terminates mTLS, the application sees the proxy's connection and must trust a header (`X-Forwarded-Client-Cert`) only from that proxy, over a channel the client cannot reach directly.
- **Key theft.** A client private key copied off a host is that identity until the certificate expires. Keep keys in memory, rotate often, use hardware-backed keys where possible.
- **Issuance policy.** The CA decides who gets which SAN. A CA that issues any SPIFFE ID to any requester makes step 3 meaningless.
- **Server verification by the client** is chapter 19; server TLS settings are chapter 18.

## 7. Checklist

- [ ] Servers that authenticate clients use `RequireAndVerifyClientCert` (or `VerifyClientCertIfGiven` with handlers that check `VerifiedChains`).
- [ ] `ClientCAs` is a dedicated client CA.
- [ ] Authorization reads `VerifiedChains`, never `PeerCertificates`, and never `Subject.CommonName`.
- [ ] Identities are URI (SPIFFE) or DNS SANs, matched exactly against an allow-list per endpoint.
- [ ] 401 for no identity, 403 for a known identity without permission.
- [ ] Client certificates are short-lived and rotated automatically.
